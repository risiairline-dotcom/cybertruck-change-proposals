**四、这次复现的四处代码问题**

**C01：回复期限检查没有覆盖全部收包路径。高优先级，合成输入已复现。**

Link.step检查pending是否满250ms，但Link.feed匹配种类、请求号、会话后直接清pending并处理回复，没有统一检查now-sent。DeviceCore.tick前置收包有期限检查，末尾transport.read后的feed没有同样检查。

复现：在1.000秒已有35状态请求；进入tick时尚未超时；模拟read或线程调度延迟到1.300秒才返回正确身份的回复。实际结果base_at=1.300、pending被清、latched=false。即300ms旧回复被重新盖上接收时刻，看起来很新。它不保证直接导致动作失控，下一轮其他旧状态仍可能触发停车；但确实破坏了“迟到回复不能刷新有效状态”的统一约束。

建议修复位置是统一收包边界，并保留“已在期限内到达的回复先解析”的原修复意图；需要区分接收证据和处理时刻，不能简单改变250ms数值。见[Link.feed](https://github.com/risiairline-dotcom/cybertruck/blob/6f8694f/pi/robot/device/link.py#L76)、[tick收包流程](https://github.com/risiairline-dotcom/cybertruck/blob/6f8694f/pi/robot/mech_core.py#L80)。

**C02：KEY_PREPARE缺少位姿无效等待的阶段期限。高优先级，合成输入已复现。**

Arrival处于KEY_PREPARE、pose_valid一直false，而base/actual/group仍按时更新、故障为0、零点有效时，advance直接return。65秒期限在WAIT_PC0分支，尚未进入该分支就用不上。回放到1000秒仍是KEY_PREPARE，无错误、无新命令。

这不是“电机持续运动1000秒”的证据，而是准备界面可能无限等待。自动Centering有60秒预算，但其处理是PAUSED，不等于Arrival合同自动结束；手动准备更不能依赖该预算。应设置阶段期限、解释位姿无效的具体原因，并通过正常合同取消/停止路径退出。见[Arrival.advance](https://github.com/risiairline-dotcom/cybertruck/blob/6f8694f/pi/robot/device/arrival.py#L122)。

**C03：传输线程异常退出后，联调表和控制权的显示状态没有统一结束。中高优先级，合成输入已复现。**

create_app.loop异常分支记录现场、取消arrival和centering、reset链路、尝试写STOP，然后break；没有同样取消sequence或清owner/token。回放结果：链路latched=true、尝试STOP，但sequence.status仍RUNNING、owner和token仍保留。线程退出后也不再推进sequence来发现失联。

因此“运行中”可能只是残留UI状态，不能推断机构仍运动；反过来也不能因为STOP写入尝试就认定已物理停住。应统一终止任务状态、撤销控制权，标记传输核心已停及停车确认未知，保留首发现场。见[异常处理](https://github.com/risiairline-dotcom/cybertruck/blob/6f8694f/pi/robot/mech_core.py#L406)。

**C13：单姿态teach保存失败会留下内存中的“新版本”。中优先级，合成输入已复现。**

teach先执行self.poses.append，再写JSON；写入异常后HTTP会报保存失败，但内存没有回滚，请求也没有进入成功缓存。同一个请求ID重试两次并模拟磁盘失败后，内存已有revision 1和2，文件不存在，运动命令数为0。由此可能出现页面仍看见未持久化版本、重启后版本消失、重试产生额外版本。program_save采用先写文件再替换内存的顺序，不能把两种保存路径混为一谈。建议统一原子保存及内存提交顺序，失败不改变可选版本。见[teach保存](https://github.com/risiairline-dotcom/cybertruck/blob/6f8694f/pi/robot/mech_core.py#L373)。

原始结果：[四项离线复现JSON](../evidence/offline_reproductions.json)。所有输入都是测试夹具，未读写设备。

**五、底盘与机构层的具体问题**

**七、什么会导致停止、拒绝或一直等待**

必须先分清五种结果：请求被拒绝，通常是动作未开始；等待，是缺少条件而没有推进；暂停，常为停车后的视觉实验暂停；故障停止，会撤销动作或零点；物理停车确认，是收到停止请求之后另行证明已经停稳。它们不能用一个“停了”概括。

| 层次 | 触发条件 | 当前结果与注意点 |
| --- | --- | --- |
| 页面 | 点停止、释放控制权 | 统一stop_control，取消联调/微调，动作锁定；正常人工停止不是电机故障 |
| 页面 | 页面隐藏、关闭、浏览器离线 | 实车调试页面release；若消息送不到，后续租约超时仍会停。切标签页也可能触发 |
| 主机租约 | 1.5秒没有有效renew | 停止、清owner/token；无论原机械表是否接近完成 |
| 主机权限 | site_ready未确认、非owner、token失效、commissioning未开放 | 请求拒绝；不能以反复点按钮解决 |
| 主机队列 | 上笔operation/commands未完成、动作间互斥 | 新动作拒绝或等待；不能插入单轴目标打断当前联调表 |
| 主机BUSY | 机构命令持续收到协议BUSY | MechanismLink把同一不可变载荷重新入队；该层没有统一总等待期限。联调和Arrival有各自期限，但普通单项请求不能假定也有相同阶段超时；需要任务级截止条件 |
| 主机串口 | pending应答达250ms | 链路reset，锁动作、请求STOP；C01说明收包边界还有漏洞 |
| 主机传输 | 读写异常、短写、线程内部异常 | 异常分支尝试STOP并退出线程；不自动恢复，C03有残留状态问题 |
| 联调条件 | boot/session/zero_version变化、手动模式退出、动作锁、零点失效、底盘未停 | Sequence失败并统一STOP |
| 联调新鲜度 | base/actual/group任一状态≥250ms | 停止并指出具体哪项过期；三者不能只检查一个总“在线” |
| 联调反馈 | 组ID超过1秒未匹配 | 停止，不重发可能已运行的动作 |
| 联调组 | 组状态FAILED/CANCELLED、板端拒绝或完成超时 | 整表失败；明确BUSY未接纳才有限重试 |
| 联调间隙 | 稳定等待≥3秒 | 停止。两轴零RPM但位置/目标或新轮次不满足，仍不能进入下一组 |
| 微调交接 | 合同SHA/检查点/五目标、空爪确认、零点或身份不符 | 拒绝开始；已开始后失效则失败 |
| 微调交接 | PREPARE/COMMIT/RETURN明确BUSY | 仅在阶段3秒内有限重试；运动GOAL不重放 |
| 微调交接 | 请求超过2秒没有确认 | 失败并停止，防止动作结果未知时重复执行 |
| 微调准备 | pose_valid=false | 目前可能一直KEY_PREPARE，见C02；并非PC0按钮坏了 |
| PC0 | 准备后60秒未按 | 板端取消reason3；主机另有65秒兜底，不是CAN超时 |
| PC0 | 启动条件变、会话变、收到STOP、启停区变 | 取消reason1/2/4/5；检查位图可进一步定位 |
| 微调动作 | 非单轴、非1～5mm、超过20次人工步数等 | 请求拒绝；不能只在上位算法去掉单轴条件 |
| 对中标定 | 矩阵不存在/SHA错误/相机或姿态不匹配/方向和尺量未确认 | 自动不可用；应补标定，不伪造reviewed标记 |
| 对中图像 | 相机身份变化、重连代次变化、帧旧/重复/编号错/遮挡 | 不生成新运动；自动停车后3秒无合格图像则暂停 |
| 对中收敛 | 超过12步、40mm、60秒 | 暂停实验，不能自动重启追赶 |
| 对中收敛 | 航向偏离本轮>1°、误差明显变大、连续两步不改善 | 暂停，检查方向映射/执行能力/观测 |
| 对中精度 | 小于最小可改善步长或超标定范围 | PRECISION_LIMIT等路径暂停，不能谎报CENTERED |
| MCU通信 | 500ms无进展有效心跳 | executor.stop(0x200)，session清零；重复progress不能无限保活 |
| MCU UART1 | RX溢出/串口错误、TX启动失败 | Comm_Fault相应2/4；锁存并清会话 |
| MCU UART2 | IMU串口错误/溢出 | Imu_Loss并Comm_Fault(8)，影响整机执行，不只是航向显示 |
| 协议 | CRC/COBS错误、超长帧 | 丢弃并计数；不是每个坏帧都立即全机停，后续超时可能停车 |
| 协议 | boot/session不符、TTL过期、非法长度或参数 | 对应拒绝；命令TTL从首字节时间计算，不能把过期目标当新目标 |
| CAN发送 | 发送期限50ms、错误/取消/队列与状态异常 | 总线故障或动作失败；发送完成不等于驱动运动完成 |
| CAN应答 | 匹配查询应答期限100ms，包含发送阶段 | BUS_ERROR_REPLY锁存；不等待到250ms才算CAN查询超时 |
| CAN接收 | 接收环容量16溢出、非法/驱动错误反馈 | 根据活动状态触发总线故障；需查看首发CAN快照 |
| 驱动反馈 | 驱动错误状态、配置不是期望的电机类型/16细分/校验方式 | 机构未就绪或故障；不能默默按旧倍率换算 |
| 底盘启动 | ARMING超过2秒 | Exec故障2；使能准备失败，不是路径终点没到 |
| 底盘运行 | 控制更新间隔>50ms或Observe失败 | Exec故障3；需要区分CPU调度、反馈和源身份 |
| 底盘运行 | IO或Odom故障 | Exec故障1，停止；看进一步odom/CAN/IMU原因 |
| 底盘路径 | 超出路径参考/走廊允许范围 | Exec故障6；简单删除会使偏离路线仍继续 |
| 底盘跟踪 | Track返回失败 | Exec故障4；Track子码决定过期/时间/参考/期限等具体原因 |
| 底盘输出 | 速度输出失败 | Exec故障5 |
| 微调ACK | 目标速度批次250ms未匹配TXOK | Track7；与整条动作10秒超时共用码，必须看冻结时间线 |
| 微调目标 | 动作超过10秒仍未完成 | Track7；可能是未收敛、量化、真实运动差异或停车稳定不满足 |
| 保持交接 | 机构保持检查失效，或持有期间丢失hold | 机构停止，底盘亦停止；不能让车继续跑而放弃机构监督 |
| 机构准备 | 无零点、反馈旧、不稳定、驱动/配置错误、底盘未停 | 拒绝动作或失效停机，详见后表 |
| 机构轴发送 | TX50ms、ACK250ms | 102/103；与104总动作期限不同 |
| 机构轴执行 | 到位期限耗尽 | 104；驱动目标账本、实际终点、到位位、新反馈轮次均可能使完成条件不成立 |
| 机构轴执行 | 非执行轴移动/漂移超过允许值 | 105；不能只检查正在运动的轴 |
| 机构轴执行 | 速度超限、越过终点过多、反向过多 | 都可能106；不能只凭名称断定电机方向反了 |

| 整组 | 任一子轴/舵机失败、基准失效、底盘移动、组期限 | 取消整组并使零点失效；原组不自动续跑 |
| 任务 | 身份错、证据旧/不匹配、物料未知、计时180秒或时钟失效 | 当前模拟任务拒绝推进/终止；移植实车后必须保留对应语义 |

同样一个“6”，可能是协议只读拒绝、机构人工停止、Exec走廊越界或Track限制。必须同时保存字段名、固件版本、boot/session、动作ID、首次故障时间和停止来源。很多历史“机构6/14”是后续停车结果，真正首发原因可能在主机租约、状态过期、底盘或CAN。

停止动作后，还要继续区分：STOP已排队、已写串口、板端已接受、四轮/两轴新反馈证明停住。Exec停止超过3秒进入LOCKED不意味着获得停车确认；Axis在缺少新反馈时可能长期STOPPING，这时应显示未知，不能把超时自动改成成功。

| 立即抛弃底盘微调与相关诊断 | 过早；替代方案未验证，底盘仍需粗停、航向、避障和可靠停车 | 冻结大改，比较两条路线的最小真实样例后择优 |
| 四周落地 | 与距11月6日约一周的窗口不匹配 | 优先单件闭环和整机任务；高阶标定、提速和亚像素研究后移 |

在简化的平面机构模型中，末端位置为x=r·cosθ、y=r·sinθ；局部变化为Δx≈cosθ·Δr−r·sinθ·Δθ，Δy≈sinθ·Δr+r·cosθ·Δθ。其二维可控性取决于有效r和真实机构几何。此式说明伸缩+转臂有可行性，但没有替本车确认旋转中心、工具偏置、舵机角度精度或标定。随动相机应建立“执行变化→当前视觉误差变化”的局部模型，不能照搬固定外置相机公式。

现有“环对画面中心→固定机械动作”的路线并非原则上错误：只要观察姿态可重复、粗停修正可信、该基准下取放动作已标定，它可以完成任务。方案A继续底盘站内修正的主要困难是当前Y未通过；方案B改用伸缩+转臂的主要困难是新增标定、舵机重复性和随动视觉。现阶段不能证明B必然更快完成，也不宜让整场任务开发继续完全等待高精度对中。

**十、按稳定跑完排序的关闭顺序**

1. **冻结比赛事实和本地基线。** 当前只以初赛稳定完成为目标，决赛资料单独保留；把用户确认的5V、三舵机规格、140/107mm行程及人工建零流程纳入边界，整理当前源码/固件/保存表/标定版本。此阶段可离线完成C01～C03及C13修复方案与针对性回归，但本轮没有修改控制代码。
2. **先形成正式任务的最小接口。** 唯一串口核心、任务owner、状态契约、正常停靠与机构回交、动作结果未知处理。不能只串网页按钮或轮流运行drive_core和mech_core抢串口。
3. **用最小实物样例选择对位方案。** 同一工位、同一观察姿态，以实际测量比较底盘小位移与伸缩+转臂局部调整，先确认可重复、无撞击、能停止。没有足够数据时不同时改算法、符号、增益和机械表。
4. **单件闭环。** 粗停→观察→对位→取料→存车→确认空爪/料槽→短距离运输→取出→对位→释放→验证。每步用真实结果推进，期间不依赖电脑接力。
5. **再扩三槽、三环、两批和返航。** 加入多颜色/黑色、不同初始误差、初赛第二层码垛；确认计数与屏幕。
6. **初赛整场计时与重复性。** 建议验收标准是同版本连续至少三轮完整完成，计数/实际物料一致，满足该场比赛时间，覆盖至少不同任务码/起始误差；这是一项拟定工程验收标准，不是规则原文，也不是已完成成绩。
7. **稳定后优化。** 用真实时间线找耗时最大项，再减少无效等待、优化安全并行动作或路线。通信/传感器保护不能以“赶时间”为由整体删除。
8. **决赛专项后置。** 初赛完成后再处理三角实物抓存、暂存区三圈、转盘目标圈识别、停留窗口内放置和撤离，不作为当前初赛完成的前置关口。

时间预算必须统计启动、扫码、导航、每站对中、24次初赛抓放事务、所有车载周转、转盘等待、释放确认及返航。单次对中10～20秒在多站叠加后可能耗尽整场预算。当前没有完整实测时间线，不能承诺现速度配置一定在180秒内跑完。

第3项“几何关系”的具体含义：O是机械臂实际旋转轴线在水平面上的位置；G是正常夹住物料后，物料中心轴在夹持高度的位置，不取某一爪尖；C是相机镜头中心的近似位置。固定同一个观察姿态，优先从CAD核对O到G的水平距离及方向、C相对G的前后/左右/上下偏置，再核对被夹物料底面距目标放置面的间隙。记录该姿态的升降、伸缩、转臂、料盘和夹爪五个目标；不混用零位、观察位和初始收拢位的测量。

O到G决定转臂小角度对应多少横向位移；C到G说明视觉目标与实际夹持点的偏移；底面间隙决定释放高度。这些量可以先从已有STEP/CAD提取，缺失部分再量测，不要求用户立即操作电机或一次提供完整三维标定。要用伸缩+转臂替代底盘微调时，还需验证小幅正反运动的重复性；仅确定几何尺寸不足以证明实际精度。

可以理解整体目标和各层关系，并不意味着实际舵机回差、载料挠度和整场成功率已经测得。已确认信息不再重复追问，后续围绕初赛最小闭环补足这些实测量。
